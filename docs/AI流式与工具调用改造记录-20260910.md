# LabCode AI 流式对话与工具调用改造记录

日期：2026-09-10 13:04
项目：`D:\工作\LabCode\desktop-app`
背景：用户要求 AI 对话像 TrieCode 一样有"可见的执行过程"（流式文字 + 工具调用执行），并解决"本地 Ollama 模型不能用 tools 模式像 TrieCode 那样操作"的问题。

---

## 一、问题根因（改造前）

| 项 | 改造前 | 问题 |
|---|---|---|
| AI 请求 | `ai:chat` 单次非流式请求（`stream:false`） | 用户看不到生成过程，等待期间无反馈 |
| 工具调用 | 提示词引导模型输出 `<|tool_calls|>` 文本标签，再正则解析 | 本地 Ollama qwen 系列**不认**该文本协议，回复只是普通文本，工具从不执行 |
| 对比 TrieCode | TrieCode 为自研单主循环 agent（模型调用→工具执行→结果回填循环），SSE 流式推送 | LabCode 缺流式、缺真 function calling、缺工具循环 |

## 二、本轮改动（3 个文件 + 1 个文档）

### 1. main/index.js —— 新增 `ai:chatStream` IPC（SSE 流式 + 真 function calling）
- `parseSSEStream(response.body)`：生成器逐行解析 SSE（`data:` 事件 → JSON → choice）
- `streamChatCompletion(sender, runId, ...)`：
  - `stream: true` + `tools` 数组 → OpenAI 兼容
  - delta 实时推送：`{runId, type:'delta', delta}` 事件
  - `delta.tool_calls` 增量拼接 → done 时输出 `{runId, type:'done', content, toolCalls}`
  - **失败自动回退**：去掉 tools + `stream:false` 重试一次（兼容不支持 function calling 的模型）
- `ai:chatCancel`：Map 标记取消
- 原 `ai:chat` 非流式保留作回退

### 2. main/preload.js —— 暴露流式接口
```js
ai.chatStream(options)  // invoke ai:chatStream
ai.chatCancel(runId)
ai.onStream(callback)   // 订阅 ai:stream，返回 listener
ai.offStream(listener)
```

### 3. renderer/js/app.js —— RealAIClient 流式化
- `_buildToolDefs()`：把 TOOL_DEFS 转 OpenAI `{type:'function',function:{...}}`（排除 ask_user）
- `_buildSystemPrompt(useNativeTools)`：双模式提示词（function calling 模式不再引导文本标签格式）
- `_buildMessages(userInput, messages, useNativeTools)`：统一消息构造（tool 结果转 user 消息）
- `_streamChat(messages)`：
  - 订阅 `ai:stream` 事件驱动 Promise，120s 超时
  - **抑制机制**：模型把工具调用输出为裸 JSON 时（Ollama qwen 实测行为），内容以 `{`/`[` 开头即暂缓上屏；done 后判定为工具调用则不显示、为纯文本则补上屏——避免把工具 JSON 当回答显示
  - done 时若 `toolCalls` 为空，用 `_parseToolCalls` 补解析裸 JSON
- `generateResponse`：**流式优先 + 非流式回退**
- `_parseToolCalls` 增强：兼容裸 JSON `{"name":"...","arguments":{...}}`（仅当 name 命中已知工具且带 arguments 才判定，避免误吞普通 JSON 回复）
- 外层 runAgentLoop 注入 `this.ai.onStreamDelta = delta => this._stream(delta,false)`，流式结果（`streamed===true`）不重复上屏

## 三、实测验证（CDP + UI 双通道）

### 3.1 流式通道（CDP 直测 chatStream）
- 事件类型：`[delta, done]`，18 个 delta 实时推送
- delta 拼接内容：`{"name": "read_file", "arguments": {"file_path": "package.json"}}` —— **Ollama qwen 把工具调用输出为裸 JSON 文本**（不走标准 `delta.tool_calls` 通道）
- 无 error

### 3.2 端到端（UI 发消息"读取文件 package.json 并总结它的内容"）
- 用户消息入气泡 ✅
- 流式 delta 经抑制机制暂缓上屏 ✅（工具 JSON 未污染界面）
- done 兼容解析 → `read_file` 工具真实执行 ✅（日志确认 `执行工具 read_file({"file_path":"package.json"})`）
- 工具结果回填 → 进入第二轮模型总结（流式上屏）✅

### 3.3 性能观察（重要）
- **qwen2.5-coder:7b 在 CPU 上推理极慢**：总结 package.json（2-3KB 内容）耗时约 **5 分钟**
- 模型对"你好"类纯对话在长上下文下回复异常（实测回"？"）——本地 7B 模型在长上下文 + tools 参数下质量退化
- **代码链路已通，瓶颈在本地模型推理速度与质量**

## 四、结论与建议

**代码层已完成对齐**：LabCode 现在具备 TrieCode 同类的 agent 循环能力——SSE 流式生成、真 function calling（含裸 JSON 兼容）、工具执行 → 结果回填 → 继续生成。

**要获得 TrieCode 级别的流畅体验，建议**：
1. **换更快/更好的本地模型**：qwen2.5-coder 7B CPU 推理太慢。可试 `qwen2.5-coder:3b`（快约 2-3 倍）或给 Ollama 配 GPU；qwen3.5:9b 更大更慢（本机已装）
2. **调大 Ollama 上下文**：`OLLAMA_CONTEXT_LENGTH=16384` 或模型 `num_ctx`，避免长对话截断导致模型困惑
3. **混合路线（推荐）**：轻量对话/小任务走本地（隐私、免费、离线），重型编程任务走云端 API（如 DeepSeek，配置 API Key 后走同一流式通道）——与 TrieCode 的"内置模型 + BYOK"双轨一致
